# Plan: Message list (from specs/message-list.md, 2026-11-13)

Status: done.

The list is copied from the frozen reference (`message-list-ref`), commits `9b408f0a57d` (row model), `83e7cfd5af3` (reducer and
scroller), `1007b6e5fa2` (components, stories, keyboard), `a32cdc39835` (conversation stories), `2da05ca0415` and `66abbe1eea7`
(enabling commits) and `36bc5e0db92` (docs and the ADR, which was 0010 at the reference and is 0001 in the package's own sequence), then adapted to the base. `develop` wins where it differs. The spec's
questions are answered: the three defects of Q1 are fixed in their own commits, `bottomThreshold` exists (Q2), the held row stays mounted
and `REVIEW.md` and `AGENTS.md` say so (Q3), the keyboard hook is the package's own copy of `develop`'s (Q4), and `useFormatDate` is in
`@rocket.chat/ui-client` (Q5). Nothing in `apps/meteor` uses the list in this branch, so no meteor file changes except through the
rebuilt `ui-client`.

What the plan does not copy from the reference:

- `useMergedRefsV2` is imported from `@rocket.chat/ui-client`, not `@rocket.chat/fuselage-hooks`.
- `MessageRowStateContext` lives in `src/Message/contexts/` (the variants' `useIsMessageEmphasized` reads it, so `Message/` must not
  import from `MessageList/`); `MessageList/` re-exports `useIsMessageHighlighted`.
- The keyboard hook is `develop`'s current `useItemListNavigation` (media Tab, Left and Right, move-row shortcut) plus the options
  `scrollToAdjacentRow`, `onMoveBetweenRows` and, added after the first review, `isAdjacentRow`, without the fallback that writes `scrollTop`; `useMessageRowListNavigation` is not
  copied (the app keeps its own); `useMessageListNavigation` returns the callback ref as the reference does, and the app's
  `useMessageListNavigation.spec.tsx` is ported, because the reference dropped that proof.
- The adjacent row of a keyboard move is found by the row model (`adjacentMessageIndex`), not by `index ± 1` in `MessageList.tsx`.
- `tests/utils/listContract.ts` carries `expectListKeyboard` only (no `listWrapper`, so no `react-virtuoso`).
- The date and the divider format the day with `useFormatDate` of `@rocket.chat/ui-client` (Q5).
- `isAtBottom` of the report is the position, the first report needs no scroll and a resize reports (Q1); the position resolves when the
  first messages are listed (Q1); the bottom has a threshold (Q2); row rendering is bounded (intent Q4). Each is its own commit.

## Risks

- virtua cannot lay out in jsdom, so what scrolls or measures is proven only by play tests, in a real browser: they must be
  deterministic. The helpers wait for the list to settle (`data-anchor` and `data-phase`), latencies are controlled by the fake
  source, and every play test is run twice at the tip. A flake means a missing wait, never a retry.
- The threshold (R80) touches the reducer's "at the bottom" in three places: acquiring the bottom, the paging at the newer edge and the
  report. The anchor's own re-application keeps the exact bottom (within 1px), so a threshold never leaves the list short. Only user input
  still releases an anchor, and nothing writes `scrollTop`. If the threshold cannot be added without breaking these, the spec keeps 1px
  and records the difference.
- Copying the reference brings its three known defects (`D1` to `D3`) and its suspected fourth; each is pinned or fixed first.
- The package copy of the keyboard hook duplicates the app's, which serves the sidebar and the side panels: a fix to one must reach the
  other until the follow-up that moves the hook to `@rocket.chat/ui-client`, after branch 09.
- `REVIEW.md` and `AGENTS.md` say "keepMounted holds no UI-state rows": step 17 rewords them for the held row, so a reviewer does not
  flag R65.
- `ui-client` changes (the scrollbars, `useFormatDate`): the meteor typecheck and the whole client suite run at the tip, with
  the dists rebuilt.
- Stopping after step 9 leaves the list complete, with the three Q1 defects and no threshold, and unused.

## Departures found in implementation

- The ADR is `docs/adr/0001-...`: the number 0010 of the reference is taken in the repository's `docs/adr/`.
- `D2` (a newer page ending in the viewer's own message) was dropped before it was recorded: such a page is added before the newer
  loader row and is classified as a change inside the rows, so it is never taken for an own message. R20 now says what is
  reachable: the handle's `scrollToBottom()` and "Jump to recent messages" ask for the latest page first. `D4` was pinned in step 5
  and fixed in step 14, so it is not in the spec any more.
- Step 8 also wrote the stories of the fixes (`RestorePositionOfAListThatMountsEmpty`, `ReportsBeingAtTheBottomAfterAJump`,
  `ReportsAfterAResize`, `BottomThreshold`), each in the commit of its fix, with its failing run recorded in the commit message.
- More fixes than planned, each with a test that failed first: the report of what is visible reads the scroll container's size, since the
  virtualizer learns of a resize a moment after the list does (step 12); the keyboard keeps trying for ten frames to reach a row the
  virtualizer is rendering; and, after the first review, an arrow reaches the row next to the focused one in the list's order (the list
  gives the hook `isAdjacentRow`), because a row kept mounted far from the viewport sits among the rendered ones and an arrow from it
  reached a row far away (R66); a list without `onJumpToLatest` stops waiting for a latest page it cannot ask for (R20; the
  rejected-promise case stays `D3`); and the position applied is the one the list is given when its first messages are listed (R61).
- After the first review the commits were reordered so the keyboard fixes sit below the docs commits, and the row-rendering commit is
  a `fix`. The proofs the review found weak were strengthened: the report of an older window waits for the new position (R56), the
  threshold play resizes into a gap smaller than the threshold (R80), and the plays no longer sleep: they wait on what they read (the
  input play is three stories). Two waits are real time on purpose: the floating date must hide within 600 ms (it would otherwise show
  for a second, R52), and a paused load stays held until the play settles it.
- The proofs the mutation check found weak were tightened in their own test commit (R11, R49, R58, R67, R70, R72).
- A story cannot tell the two-step commit of R38 from a single one in this version of the virtualizer, which keeps the position either
  way; the table row of `planRowsCommit` proves the staging, and the play proves the outcome.
- Review round 1. A page of older messages lands under the older loader, so the comparison that classifies a change sets the row above
  the messages aside: before, every page but the last was a change inside the rows, so the virtualizer did not keep the rows in place,
  the list put the top message's row back a frame later (moving what it says by the height of a day divider it lost) and checked for
  the next page from the position before that correction, asking for page after page. The plays read where a message's text is,
  below the dividers of its row: `HeaderReplacesTheLoader` had failed under UTC only because it read the top of the row. The spinner
  of the first page sits at the top (R4). The list also places itself again when its first messages arrive after it stopped, and
  when its viewport gets a size it did not have, so it lands before it checks for a page (R29).
- R51's reduced motion is a CSS media query, which jsdom and the plays do not observe: it is a manual check.
