## Risks

- jsdom cannot lay out the virtualizer, so the room's specs run the package's list with `virtua`'s `Virtualizer` replaced (a one-line
  `jest.mock`) and a double for the handle; what scrolls stays proven by the package's play tests. The whole room is never run in a
  browser here: QA does the manual check (the scope's list).
- Read state is the most fragile: a double list cannot tell that the real list reports on its own. `getVisibility()` is asked
  synchronously, as `message-list` R57 promises; the spec drives the callbacks of the real manager (not a mock) so the gate is proven end to end.
- The reducer-level D3 is unreachable from the room (R42); the spec rejects `getMore` after the clear to keep it so.
- A row's markers are read from a store fed by the list's subscription prop, so a row costs nothing when another subscription of the client
  changes, as the rows of `develop`'s list did (the first version searched every subscription per row).
- The e2e page object selector is changed unrun; QA lists it.
- If work stops after step 7 the list parts are unused and nothing changes for viewers; after step 8 the old list is dead code; stopping
  after step 9 leaves the history manager's dead DOM code (harmless).
- `oxlint --fix` rewrites `SelectedMessagesContext.tsx` and `lib/autotranslate/autotranslate.ts`; those edits stay out of every commit.

## Departures found in implementation

- A row reads its four markers from a store of the room's subscription that the list holds (`MessageMarkers`), instead of receiving them
  as props: `renderMessage` must stay stable (R52), and a marker read through props would need it to change with the subscription. The
  first version read the client's subscriptions store from each row, which ran a search over every subscription for each mounted row
  whenever any subscription changed; `develop`'s rows only ever computed their markers when the room's own subscription changed, so the
  store is fed from the list's `subscription` prop and an unrelated change costs the rows nothing.
- The meteor specs run the real list through the package's own seam, by path: `jest.mock('@rocket.chat/ui-message-list/dist/MessageList/MessageListVirtualizer', ...)`
  with `MessageListRows`. A `virtua` mock does not reach the package's copy of `virtua`.
- Step 1 dropped `contexts.spec.tsx`: the option is proven by `useCanReplyToBroadcast.spec.tsx` and the provider's stability spec.
- Found while replacing the old list: it does not page while hidden behind the contextual bar (`useGetMore` returned for a viewport of no
  size) and the engine did. `message-list` R81 and a reducer guard were added as a fix commit below the feature (reordered below step 7).
- The proofs of `message-variants` R25, R26, R40, R46, R48 and R50 that lived in the deleted `MessageList.spec` and `MessageListItem.spec`
  moved to `RoomMessageRow.spec`, `RoomMessageList.spec` and `ComposerSelectMessages.spec`; the deleted `useGetMore`, `useHasNewMessages`
  and `useIsAtBottomRef` specs are replaced by the list's (R30, R31, R19 to R22, R60, R81) and the room's (R39, R43).
- Review round 1: the engine also needed `countsAsArrival` (message-list R19, R21, R22) so that a thread reply that shows in the room
  neither raises "New messages" nor takes the list to the bottom, as `develop`'s `useHasNewMessages` ignored every streamed message with a
  `tmid`; the room's difference of Q3 is gone. The reducer places the list again when a hidden viewport gets its size, and checks for
  a page once it has (R81). The retry of a failed first page (R59) skips a room the viewer cannot preview. The jump's once-per-target guard and the mark-as-read input
  attempt have proofs that do not rest on timing left over from opening. The stale-flag reset in the scroller's tail classification
  (a newer page that ends with a message that is no arrival) follows from the code and has no jsdom proof, since paging needs a measured
  viewport.
- Review round 2: with newer messages remaining the list does not take the viewer's own message for an append (it lands before the newer
  loader row), so nothing in the room brought it back to the latest messages and R43 had only unit proofs of the author test. The room
  now listens to the stream as `develop`'s `useHasNewMessages` did and calls the handle's `scrollToBottom()` for the viewer's own message
  that is neither an edit nor a thread reply (`useScrollToBottomOnOwnMessage`). The spec sends the message in an older window and expects
  the latest window to load and the list to end at the bottom; it failed before the hook.
- Review round 1, after the engine's fixes: the room passes `deferPagingUntilInput` (R60, a user decision) and `develop`'s space at
  the ends (R57); the first input in an empty room whose first page failed then asks the list for an older page in the same moment as
  the room's retry (R59), so the room starts no page while the history manager loads one (R39). The floating date follows `develop`'s
  rules from the engine (message-list R51, R52). The quote of a "Reply in direct message" link, which
  relied on the room body rendering again after the composer registered, is fixed below this branch's feature, with the upload progress
  and the drop area that had the same defect.
- Second review of round 1: "Jump to recent messages" sat 24px higher than on `develop` while newer messages remained, because the
  24px `develop` keeps below the list shortened the list's own box, where the list draws the button. The room no longer shortens the
  element around the list and passes 34px of end space instead (10 + 24), which rests the last row and the button where `develop` draws
  them (R57). The floating date was drawn behind the upload progress and the unread banner; `RoomBody` measures them with a callback
  ref and the list rests its date below them (R61, message-list R85).
- The stability spec's readers are one test-only component, `tests/mocks/client/RelatedDataReader.tsx`, parameterised by what it reads.
